# AGENTS.md — правила работы ИИ-агента

Правила действуют в каждой сессии и для каждого агента, включая подагентов. Явная команда пользователя в текущем сообщении важнее этого файла, **кроме раздела «Git и GitHub»**: снять этот запрет может только изменение самого файла пользователем.

## Источники правды

Читать перед началом любого шага, в таком порядке приоритета:

1. Техническое задание курса в части обязательных требований (его положения зафиксированы в [Plan.md](Plan.md) и [README.md](README.md)).
2. [Plan.md](Plan.md) — решения, правила данных, текущий шаг и его критерии.
3. [DESIGN.md](DESIGN.md) — визуальные правила.

Нашли расхождение между документами — остановиться и сообщить, а не выбирать молча.

## Выполнение шагов

- Выполнять **только один утверждённый шаг** из Plan.md.
- **Не переходить к следующему шагу без команды пользователя**, даже если текущий завершился успешно и время осталось.
- Не делать работу будущих шагов «заодно». Замечания записывать в отчёт.
- Новая зависимость, изменение модели данных или архитектурного решения вне Plan.md — сначала согласовать.
- Устанавливать пакеты только с точной версией, без `^` и `~`.
- Удалять за собой временные файлы и останавливать запущенные собой процессы. Чужие процессы не останавливать.

## Git и GitHub — абсолютный запрет

- **Никогда не выполнять Git-команды**, в том числе только читающие: `git status`, `git log`, `git diff` и любые другие.
- **Никогда не создавать commit, push, branch или merge** — ни напрямую, ни через инструменты и скрипты.
- **Не подключаться к GitHub**: ни `gh`, ни API, ни веб-интерфейс, ни MCP-интеграции.
- Не менять содержимое каталога `.git` и настройки Git.
- Фиксацию версии и отправку на проверку **выполняет пользователь**. Агент может только подготовить чек-лист.

Правка файла `.gitignore` не является Git-командой и допустима, если её требует шаг.

## Данные пользователя

**Не изменять пользовательские данные без разрешения.** Разрешение даётся в текущем сообщении или на конкретное действие в этом шаге; разрешение из прошлого шага не переносится.

### Базы данных

| База | Назначение | Что можно агенту |
|---|---|---|
| `studio_crm` | Рабочая, данные пользователя | По умолчанию только чтение. Любое изменение — только с отдельного разрешения |
| `studio_crm_agent` | Все автоматические проверки с изменением данных, включая dev и production | Менять данные, запускать seed, reset и тесты без отдельного разрешения |

**Запрещено всегда, даже с общим разрешением на изменение данных:** удалять и пересоздавать базу `studio_crm`, в том числе `DROP DATABASE`, `dropdb` и `prisma migrate reset`.

Перед любой изменяющей данные командой проверить, на какую базу указывает `DATABASE_URL`. Тесты запускать только через `npm test`, обёртка которого проверяет имя базы. Не обходить эту проверку.

Сброс `studio_crm` выполняется только с отдельного разрешения пользователя на этот сброс. Подтверждение `db:reset` вводит сам пользователь в интерактивном терминале: флага `--yes` нет, имитировать терминал или ввод нельзя.

Требуют отдельного разрешения:

- на `studio_crm`: `npm run db:seed`, `npm run db:reset`, `npm run db:deploy`, создание, изменение и удаление записей через интерфейс или прямые запросы;
- создание баз данных и ролей PostgreSQL вне шага 02; удаление и пересоздание `studio_crm_agent`;
- установка или смена версии Node.js вне шага 02;
- запуск и остановка службы PostgreSQL;
- перезапись `.env`, а также удаление файлов, которых не создавал агент.

**Заранее разрешено только на шаге 02 и только после команды его начать:** установка Node.js 24 LTS через nvm; создание двух локальных баз PostgreSQL 16 и необходимых ролей. Существующие базы нельзя удалять или пересоздавать.

Не применять в проекте: `prisma migrate reset` и `prisma db push`. `prisma migrate dev` запускать только на `studio_crm_agent`.

Если нужно проверить изменяющий данные сценарий, использовать `studio_crm_agent`. Если это невозможно — выполнить остальные проверки и сообщить, что осталось непроверенным.

Защиты Prisma от опасных действий агентов не обходить; согласие на такие действия (например, переменные вида `PRISMA_USER_CONSENT_*`) может дать только пользователь.

Содержимое `.env` не выводить в отчёты и логи. Реальные секреты в репозиторий не добавлять.

## Обязательные технические требования

Менять запрещено:

- Next.js, React, TypeScript, PostgreSQL, Prisma, Zod;
- Node.js 24 LTS, локальный PostgreSQL 16, без Docker;
- статус сделки вычисляется из `Stage.type`, отдельное поле не добавлять;
- конвертация лида атомарна и защищена от повторных и параллельных вызовов на сервере; компания при конвертации обязательна: новая или существующая;
- `Contact.accountId` необязателен; `Opportunity.accountId` и `Opportunity.contactId` — независимые связи, совпадение компаний не проверять;
- компанию со связанными контактами или сделками удалять нельзя;
- `db:seed` работает только с пустой базой; `db:reset` восстанавливает демонстрационные данные, не удаляет базу и схему и вне `studio_crm_agent` требует подтверждения пользователя, которое нельзя обойти флагом `--yes`;
- после изменения записей интерфейс и дашборд показывают актуальные данные при повторном запросе;
- автотесты только на `node:test` + `tsx`;
- точно `prisma@6.19.3` и `@prisma/client@6.19.3`;
- `DATABASE_URL` читается в `schema.prisma` через `env("DATABASE_URL")`;
- **не использовать** `@prisma/adapter-pg`, `PrismaPg`, `prisma.config.ts`;
- точно `chart.js@4.5.1` и `react-chartjs-2@5.3.1`;
- на дашборде агрегация на сервере через Prisma `groupBy` и `aggregate`;
- никаких WebSockets, Live Subscriptions, push-уведомлений;
- серверная валидация через Zod; ошибки бэкенда показываются пользователю;
- весь интерфейс на русском, значения enum в коде — по Plan.md.

Правила данных из разделов 1.3–1.8 Plan.md реализуются только в серверном слое и применяются единообразно: через интерфейс, Kanban, быстрые действия и seed.

## Проверка результата

Результат считается готовым только после проверки, а не после написания кода.

1. `npm run lint`, `npm run typecheck` и `npm test`, когда скрипты уже существуют.
2. **Dev:** запустить `next dev` с `DATABASE_URL` на `studio_crm_agent` и пройти затронутый сценарий.
3. **Production, когда это применимо:** `next build`, затем `next start` с `DATABASE_URL` на `studio_crm_agent`, тот же сценарий. Применимо для любого шага, меняющего код приложения. Неприменимо только для правок документации.
4. Проверить критерии приёмки шага из Plan.md по одному.
5. Для интерфейса: просмотреть экран на ширине 1440, 1024 и 390 px и свериться с DESIGN.md.
6. После исправления бага заново проверить всё, что могло пострадать.

Нельзя заявлять о проверке, которая не выполнялась. Если проверка невозможна, сказать об этом и назвать причину.

## После каждого шага

**Обновить Plan.md:** статус шага в таблице и запись в журнале (что сделано, что и как проверено, ошибки и ограничения). Если изменилось решение, поправить раздел решений, а не только журнал.

Затем дать отчёт на русском:

- что сделано и какие файлы изменены;
- какие проверки выполнены и с каким результатом, отдельно dev и production;
- **ошибки и ограничения**: что не работает, что не проверено, что сделано иначе, чем в плане;
- что требует решения пользователя;
- какой шаг следующий — и остановиться, ожидая команды.

## Ошибки и ограничения

- Сообщать о них сразу и прямо, с текстом ошибки. Не скрывать падающие проверки и предупреждения.
- Не обходить проблему отключением проверок, `@ts-ignore`, `any`, отключением правил линтера или ослаблением критериев приёмки без согласования.
- Если шаг нельзя завершить, отметить его в Plan.md как `заблокирован`, описать причину и варианты.
