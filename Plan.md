## 1. Продуктовые решения

Этот раздел — единый источник правды. Код, seed, интерфейс и README должны ему соответствовать.
Значения enum в базе и коде — английские, подписи в интерфейсе — русские.

### 1.1. Сущности

`Lead`, `Account`, `Contact`, `Opportunity`, `Stage`, `Activity`. В интерфейсе: лид, компания, контакт, сделка, стадия, активность.

### 1.2. Источник лида (`source`) — обязательное поле

| Значение | Подпись |
|---|---|
| `site` | Сайт |
| `email` | Почта |
| `phone` | Телефон |
| `referral` | Рекомендация |
| `manual` | Вручную |

### 1.3. Статусы лида (`status`)

| Значение | Подпись | Как устанавливается | Можно конвертировать |
|---|---|---|---|
| `new` | Новый | По умолчанию при создании | Да |
| `in_progress` | В работе | Вручную | Да |
| `qualified` | Квалифицирован | Вручную | Да |
| `disqualified` | Отклонён | Вручную | Нет, сначала вернуть в работу |
| `converted` | Конвертирован | **Только** транзакция конвертации | Нет, конечный статус |

- Статус `converted` нельзя выбрать в форме и нельзя снять.
- Основные поля конвертированного лида доступны только для чтения.
- Конвертация не требует статуса `qualified`, потому что основной сценарий задания идёт от создания лида сразу к конвертации.

### 1.4. Стадии воронки (`Stage`) и результат сделки

Отдельного поля статуса у сделки **нет**. Статус выводится из типа текущей стадии, поэтому стадия и статус не могут разойтись.

| Порядок | `key` | Подпись | `type` | Статус сделки |
|---|---|---|---|---|
| 1 | `brief` | Бриф | `open` | Открыта |
| 2 | `concept` | Концепция и смета | `open` | Открыта |
| 3 | `approval` | Согласование | `open` | Открыта |
| 4 | `contract` | Договор | `open` | Открыта |
| 5 | `won` | Выиграна | `won` | Выиграна |
| 6 | `lost` | Проиграна | `lost` | Проиграна |

- Стадии — справочник без CRUD в интерфейсе. Они вставляются SQL-шагом в миграции и не зависят от seed: база после миграции уже работоспособна.
- Фильтр «Статус» строится как `where: { stage: { type } }`, фильтр «Стадия» — как `where: { stageId }`.

### 1.5. Правила перехода между стадиями

Любая смена стадии идёт через одну серверную функцию. Её используют Kanban, карточка сделки и быстрые действия.

| Переход | Проверка на сервере | Побочный эффект |
|---|---|---|
| Открытая → открытая | Нет | — |
| Любая → `won` | `amount > 0`; контакт привязан | `closedAt = now`; `lostReason = null` |
| Любая → `lost` | `lostReason` не пустая после `trim` | `closedAt = now`; причина сохраняется |
| `won`/`lost` → открытая | Подтверждение в интерфейсе | `closedAt = null`; `lostReason = null` |

Инварианты редактирования:

- Новая сделка создаётся только в открытой стадии. Стадии нет в форме редактирования, её меняет только быстрое действие.
- У сделки в `won` нельзя очистить сумму или контакт. У сделки в `lost` нельзя очистить причину.
- `Opportunity.accountId` и `Opportunity.contactId` — независимые связи. Совпадение компании контакта и компании сделки не требуется: к сделке можно привязать контакт другой компании или контакт без компании.
- Смена или очистка компании контакта не меняет его сделки.

### 1.6. Конвертация лида

**Режимы компании:**

При каждой конвертации создаётся контакт. Компания обязательна: создаётся новая либо используется существующая. Других режимов нет. Основной демонстрационный сценарий создаёт новую компанию и контакт, как требует фаза 6.

| Режим | Значение | Что происходит |
|---|---|---|
| Новая компания | `new` | Создаётся `Account`, контакт и сделка связываются с ним. Режим по умолчанию |
| Существующая компания | `existing` | Контакт и сделка связываются с выбранной компанией, новая не создаётся |

**Обязательные данные:**

| Условие | Что требуется |
|---|---|
| Всегда | Имя контакта; email или телефон; режим компании |
| `new` | Название компании |
| `existing` | Компания, существующая в базе на момент транзакции |
| Создаётся сделка | Название сделки и открытая стадия |

Диалог заполняется данными лида, недостающее можно ввести прямо в нём. Если название компании лида без учёта регистра совпадает с существующей, диалог предлагает выбрать её, но сам режим не меняет.

**Транзакция.** Всё выполняется в одной интерактивной транзакции `prisma.$transaction`. Либо применяются все изменения, либо ни одно:

1. Условный `updateMany` по `id` и `status in (new, in_progress, qualified)` переводит лид в `converted`. Если обновлено 0 строк, транзакция откатывается с понятной ошибкой.
2. По режиму создаётся `Account` или проверяется выбранная компания.
3. Создаётся новый контакт `Contact`, связанный с этой компанией.
4. Если отмечено «Создать сделку», создаётся `Opportunity` в выбранной открытой стадии. Сумма по умолчанию берётся из `budget`.
5. Активности лида переносятся на сделку, а если её нет — на контакт. Так открытые задачи не теряются.
6. В лиде сохраняются `convertedAt` и ссылки на связанные записи.

**Защита от повторных и параллельных вызовов.**

- Шаг 1 выполняется первым и блокирует строку лида. Параллельный вызов ждёт завершения первой транзакции, затем PostgreSQL заново проверяет условие. После успешной конвертации это даёт 0 строк и понятную ошибку. Если первая транзакция откатилась, второй вызов может выполниться.
- Повторный вызов отклоняется тем же условием. Интерфейс дополнительно блокирует кнопку на время запроса, но защитой считается только проверка на сервере.
- **Защита опирается на статус, а не на ссылки**: ссылки могут обнулиться после удаления записей (см. 1.8).

### 1.7. Активности

- `type`: `note` (заметка) или `task` (задача).
- Активность принадлежит **ровно одной** записи: лиду, компании, контакту или сделке. Гарантируется CHECK-ограничением в миграции.
- Задача обязана иметь `dueDate`. У заметки `dueDate` пуст, а `done` всегда `false`. Также гарантируется CHECK-ограничением.
- `dueDate` хранится как дата без времени (`@db.Date`), это исключает сдвиг на сутки из-за часового пояса.
- «Сегодня» определяется по часовому поясу `APP_TIME_ZONE` (по умолчанию `Europe/Moscow`).
- Просроченная задача: `type = task`, `done = false`, `dueDate` раньше сегодняшней даты. Задача на сегодня просроченной не считается.

### 1.8. Правила удаления

Каждое правило закреплено внешним ключом в БД. Перед удалением интерфейс показывает, что будет заблокировано или удалено вместе с записью.

| Связь | Обязательна | `onDelete` | Поведение |
|---|---|---|---|
| `Contact.account` | Нет | `Restrict` (задаётся явно) | Компанию нельзя удалить, пока есть контакты. Контакты не отвязываются молча |
| `Opportunity.account` | Да | `Restrict` | Компанию нельзя удалить, пока есть сделки |
| `Opportunity.contact` | Нет | `Restrict` | Контакт нельзя удалить, пока он привязан к сделкам |
| `Opportunity.stage` | Да | `Restrict` | Стадии не удаляются |
| `Activity.lead/account/contact/opportunity` | Ровно одна | `Cascade` | Активности удаляются вместе с записью |
| `Lead.convertedAccount/Contact/Opportunity` | Нет | `SetNull` | Лид остаётся `converted`, ссылка становится пустой |

Почему `Opportunity.contact` — `Restrict`, а не `SetNull`: `SetNull` создал бы выигранную сделку без контакта и нарушил правило `won`. Порядок удаления: сделки → контакты → компания.

При каждой конвертации лид связывается с контактом и компанией, поэтому их пустая ссылка означает удаление: карточка показывает «Компания удалена», «Контакт удалён». Сделка необязательна, поэтому для неё текст нейтральный: «Сделка не создана или удалена».

Удаление лида не затрагивает созданные из него компанию, контакт и сделку.

### 1.9. Быстрые действия

Создать сделку · сменить стадию · добавить заметку · добавить задачу · конвертировать лид.

### 1.10. Показатели дашборда

| Показатель | Определение | Метод |
|---|---|---|
| Всего лидов | Все лиды, включая конвертированные | `lead.aggregate` |
| Открытых сделок | Сделки в стадиях `type = open` | `opportunity.aggregate` |
| Сумма открытых сделок | Сумма `amount`; пустая сумма считается как 0 | `opportunity.aggregate` |
| Просроченных задач | По определению из 1.7 | `activity.aggregate` |
| Сделки по стадиям (диаграмма и сводка) | Количество и сумма по всем шести стадиям | `opportunity.groupBy` |
| Статусы лидов (диаграмма и сводка) | Количество по пяти статусам | `lead.groupBy` |
| Источники лидов (сводка) | Количество по пяти источникам | `lead.groupBy` |
| Новые лиды | 5 последних созданных, любого статуса | `lead.findMany` |
| Просроченные задачи | Список, сначала самые старые | `activity.findMany` |
| Зависшие сделки (опционально) | Открытые, `updatedAt` старше 14 дней | `opportunity.findMany` |

## 2. Модель данных

Служебные поля `id` (cuid), `createdAt`, `updatedAt` есть у всех моделей, кроме `Stage`.

| Модель | Обязательные поля | Необязательные поля |
|---|---|---|
| `Lead` | `contactName`, `source`, `status` + email или телефон (проверка Zod) | `companyName`, `email`, `phone`, `budget`, `venue`, `eventDate`, `workFormat`, `comment`, `convertedAt`, `convertedAccountId`, `convertedContactId`, `convertedOpportunityId` |
| `Account` | `name` | `industry`, `website`, `email`, `phone`, `city`, `comment` |
| `Contact` | `fullName` | `accountId`, `position`, `email`, `phone`, `comment` |
| `Opportunity` | `name`, `accountId`, `stageId` | `contactId`, `amount`, `venue`, `eventDate`, `workFormat`, `expectedCloseDate`, `lostReason`, `closedAt`, `comment` |
| `Stage` | `id`, `key` (unique), `name`, `order` (unique), `type` | — |
| `Activity` | `type`, `body`, `done` (по умолчанию `false`) + ровно один родитель | `dueDate`, `leadId`, `accountId`, `contactId`, `opportunityId` |

- Денежные поля: `Decimal(14, 2)`, валюта одна — рубли.
- Индексы: все внешние ключи, `Lead.status`, `Lead.source`, `Activity(type, done, dueDate)`.

## 3. Архитектура

| Решение | Выбор |
|---|---|
| Среда выполнения | Node.js 24 LTS, версия в `.nvmrc` и `engines` |
| СУБД | Локальный PostgreSQL 16, без Docker |
| Приложение | Next.js App Router, React, TypeScript `strict` |
| Чтение данных | Серверные компоненты, вызывающие `src/server/queries/*` |
| Запись данных | Server Actions (`src/server/actions/*`) → Zod → сервисы (`src/server/services/*`) → Prisma |
| Бизнес-правила | Только в сервисах. Компоненты и actions правил не содержат |
| Результат action | `{ ok: true, data }` или `{ ok: false, message, fieldErrors? }` |
| Ошибки | Доменные ошибки и коды Prisma (`P2002`, `P2003`, `P2025`) переводятся в русские сообщения |
| Decimal | Перед передачей в клиентские компоненты преобразуется в `string` или `number`, сам объект `Decimal` не передаётся |
| Актуальность | После изменения записей интерфейс и дашборд показывают актуальные данные при повторном запросе. Способ обеспечения выбирается при реализации. Real-time нет |
| Фильтры и поиск | Состояние в `searchParams`, выборка на сервере, `contains` + `mode: "insensitive"` |
| Стили | Tailwind CSS с CSS-переменными из DESIGN.md, свои примитивы в `src/components/ui` |
| Kanban | `@dnd-kit/core` плюс действие «Сменить стадию» как доступная альтернатива перетаскиванию |
| Иконки | `lucide-react` |
| Автотесты | Встроенный `node:test` через `tsx`, без отдельного фреймворка. Тесты вызывают сервисы напрямую, поэтому сервисы не импортируют `next/*`: такие вызовы находятся в actions |

Маршруты: `/` → редирект на `/dashboard`; `/leads`, `/accounts`, `/contacts`, `/deals` (плюс `/new`, `/[id]`, `/[id]/edit`); `/pipeline`; `/search`.

### Локальные базы данных

| База | Назначение | Переменная | Кто и что может делать |
|---|---|---|---|
| `studio_crm` | Рабочая | `DATABASE_URL` | **Удалять и пересоздавать запрещено.** Изменение данных и применение миграций — только с разрешения пользователя |
| `studio_crm_agent` | Все автоматические проверки с изменением данных, включая проверки в dev и production | `TEST_DATABASE_URL` | Агент свободно меняет данные, seed и reset выполняются без отдельного разрешения |

- Схема Prisma всегда читает `env("DATABASE_URL")`. Тестовая обёртка `scripts/with-test-db` подставляет значение `TEST_DATABASE_URL` в `DATABASE_URL` только для своего процесса и отказывается работать, если имя базы не `studio_crm_agent`.
- Для запуска и ручной проверки проверяющему достаточно `studio_crm`. Вторая база нужна для `npm test` и проверок агента.

### Применение схемы и данные

| Команда | Что делает | Ограничения |
|---|---|---|
| `npm run db:migrate` | `prisma migrate dev` — создание миграции при разработке | Агент запускает только на `studio_crm_agent` |
| `npm run db:deploy` | `prisma migrate deploy` — применение готовых миграций без сброса | Безопасный способ обновить `studio_crm` |
| `npm run db:seed` | `prisma db seed` — контрольные данные **только в пустую базу**: все таблицы, кроме справочника `Stage`, не содержат строк | Если данные уже есть, ничего не меняет и завершается с ошибкой |
| `npm run db:reset` | `prisma db seed -- --reset` — очистка строк всех таблиц, кроме `Stage`, и вставка контрольных данных в одной транзакции | Базу и схему не удаляет, миграции не применяет. Для любой базы, кроме `studio_crm_agent`, сначала требует подтверждения пользователя (шаг 04) |

`prisma migrate reset` и `prisma db push` в проекте не применяются: первая удаляет схему вместе с данными, вторая обходит миграции. Обе команды сброса отказываются работать, если хост `DATABASE_URL` не локальный.

### Шаг 02. Каркас проекта и локальное окружение

**Зависит от:** команды пользователя на запуск шага.

**Разрешено пользователем для этого шага:** установка Node.js 24 LTS через nvm; создание двух локальных баз PostgreSQL 16 и необходимых ролей. Существующие базы нельзя удалять или пересоздавать. Версию nvm по умолчанию шаг не меняет, активная версия выбирается через `.nvmrc`. Запуск службы PostgreSQL в это разрешение не входит: если она остановлена, спросить пользователя.

- **Frontend:** Next.js + React + TypeScript `strict` с алиасом `@/`, временная страница-заглушка на русском.
- **Backend:** нет. Клиент Prisma подключается на шаге 03, когда появятся модели.
- **Database:**
  - инструкция для локального PostgreSQL 16 без Docker;
  - отдельная роль с `CREATEDB` (нужна для shadow-базы `prisma migrate dev`);
  - базы `studio_crm` и `studio_crm_agent`. Перед созданием проверить, существуют ли они. Существующие не удалять и не пересоздавать, а при несовпадении владельца или локали остановиться и сообщить;
  - `schema.prisma` с `env("DATABASE_URL")`.
- **Конфигурация:**
  - `.nvmrc` со значением `24`, `engines` в `package.json`;
  - `.npmrc` с `save-exact=true`; все версии зафиксированы без `^` и `~`;
  - `tsx` для seed и тестов;
  - точно: `prisma@6.19.3`, `@prisma/client@6.19.3`, `chart.js@4.5.1`, `react-chartjs-2@5.3.1`;
  - `.env.example` с `DATABASE_URL`, `TEST_DATABASE_URL` и `APP_TIME_ZONE`;
  - в `.gitignore` добавить `.env.local` (сейчас не покрыт правилом `.env.*.local`);

**Автотесты** (`npm test`, база `studio_crm_agent`):

| Режим | Сделка | Ожидаемый результат |
|---|---|---|
| `new` | Да / нет | Создаются новая компания и контакт; сделка — по опции |
| `existing` | Да / нет | Число компаний не меняется; контакт и сделка связаны с выбранной |
| Режим не указан или неизвестен | Да / нет | Отклонено, ничего не изменилось |

| `existing` с несуществующей компанией | Да / нет | Отклонено, ничего не изменилось |

| Лид `disqualified` (L5) | Нет | Отклонено, ничего не изменилось |

Также автотестами проверяются:

- **атомарность:** при искусственном сбое создания сделки нет новых записей, лид остаётся в прежнем статусе, активности на месте;
- **повторный вызов:** отклоняется, новых записей нет;
- **параллельные вызовы:** два одновременных вызова для одного лида через `Promise.all` дают ровно один успех, одну понятную ошибку и один набор записей;
- **перенос активностей:** на сделку, а без сделки на контакт;
- **после удаления:** удаление созданного контакта не позволяет конвертировать лид снова.

**Приёмка:** все критерии фазы 6 выполнены в режиме по умолчанию `new`; режим `existing` работает как разрешённое расширение: контакт связывается с уже существующей компанией.
